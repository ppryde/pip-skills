# Covenant discover: Steps D1-D4

Discovery is a lightweight alternative to a full Inquisition audit. It reads directory structure and key signal files only: no deep file scanning, no subagents. Its purpose is a working `.architecture/config.yml` so that Inquisition can run.

## Step D1: Scan Directory Structure

Directories only, three levels deep, pruning noise (discovery does not read file contents):
```bash
find . -maxdepth 3 \( -name .git -o -name node_modules -o -name vendor -o -name __pycache__ -o -name .venv \) -prune -o -type d -print
```

## Step D2: Detect Pattern Signals

Read `<plugin-root>/skills/doctrines/INDEX.md` (see `../../_shared/config.md`). Do not open doctrine files. Each doctrine row carries `dir signals`, `file signals` and `anti-signals`.

1. Match a signal against the scan by path suffix: `domain/commands/` matches `./src/app/domain/commands`. A signal listing alternatives ("`a/` or `b/`") counts once.
2. Score each doctrine:
   - **Strong match**: 1+ file signal OR 3+ directory signals
   - **Possible match**: 2 directory signals, no file signals
   - **Weak / no match**: 0-1 directory signals and no file signals
3. Any anti-signal present downgrades the match one level.

File signals are matched by the existence of a matching filename in the tree (`find . -maxdepth 3 -name '<glob>'` is enough); do not read file contents.

Also check key signal files (existence and location only):
- `pyproject.toml`, `pom.xml`, `package.json`, `go.mod`: infer language
- `docker-compose.yml` at root: containerisation, possible Microservices signal
- Single `Dockerfile` at repo root: monolith-leaning; multiple `Dockerfile`s in service subdirectories: Microservices-leaning

## Step D3: Present Findings for Confirmation

Present the detected patterns and proposed targets **before writing anything**:

```
Discovery complete: found N directories.

Detected patterns:
  ✓ <doctrine>  : <signals found>
  ? <doctrine>  : <partial signals> (include? [y/n])
  ✗ <doctrine>  : <why skipped>

Proposed targets:
  <doctrine> → <dir>/, <dir>/

Does this look right? You can:
  1. Confirm and generate .architecture/config.yml
  2. Add a pattern I missed (which one?)
  3. Remove a pattern (which one?)
  4. Adjust targets for a specific pattern
```

Do not write the config until the user confirms. Support multiple rounds of adjustment.

## Step D4: Generate Config

Once confirmed, write `.architecture/config.yml` with the agreed doctrines and targets, using the schema in `../../_shared/config.md` (no `layers:` key). Always include the `exclude:` block with the common defaults. Derive the `doctrines:` entries from what was detected and confirmed, not from an example:

```yaml
# Generated by /puritan:covenant discover
# Review and adjust targets before running /puritan:inquisition

doctrines:
  - name: <detected-doctrine>
    enabled: true
    targets:
      - <confirmed-dir>/

exclude:
  - "**/migrations/**"
  - "**/vendor/**"
  - "**/*.generated.*"
  - "**/node_modules/**"
```

After writing, tell the user:
> "Config written to `.architecture/config.yml`. Run `/puritan:inquisition` to begin the audit."
